# Звіт: Порівняння паралельного та послідовного завантаження даних

## 1. Обрані адреси для тестування
1. `https://jsonplaceholder.typicode.com/posts/1`
2. `https://jsonplaceholder.typicode.com/users/1`
3. `https://jsonplaceholder.typicode.com/todos/1`
4. `https://jsonplaceholder.typicode.com/posts/999999` (неіснуючий ресурс для перевірки обробки помилок)

## 2. Результати вимірювання часу (3 запуски)

| Запуск | Паралельний режим (Parallel), мс | Послідовний режим (Sequential), мс |
| :--- | :--- | :--- |
| **Запуск 1** | 325.45 | 87.34 |
| **Запуск 2** | 75.55 | 86.74 |
| **Запуск 3** | 33.87 | 84.21 |
| **Середнє значення** | **144.96 мс** | **86.10 мс** |

*Примітка: У тестах успішно перевірено ізоляцію помилок. Наявність неіснуючого запиту (4-й URL з помилкою 404) коректно перехоплюється механізмом обробки, повертає `ok: false` із описом помилки, але не зупиняє виконання решти запитів.

## 3. Висновки

* Коли доцільно використовувати паралельний режим (`Promise.all` / `Promise.allSettled`): паралельний режим відмінно підходить для завантаження незалежних один від одного ресурсів. На першому «холодному» запуску він демонструє реальну швидкість мережевих запитів. Подальше зниження часу на наступних запусках пов'язане з кешуванням. Головна перевага паралельності - усі запити йдуть одночасно, а загальний час виконання обмежений часом найдовшого запиту, що економить час клієнта при масових запитах до різних мікросервісів.

* Коли доцільно використовувати лише послідовний режим: послідовний режим необхідний у ситуаціях, коли існує чітка логічна залежність між результатами (наприклад, другий запит потребує ID, отриманого з першого). Також послідовне виконання використовують для того, щоб не створювати різкого пікового навантаження на слабкі сервери або не перевищувати ліміти кількості одночасних з'єднань (Rate Limiting) від одного клієнта.
